## 3. P1：登录、连接和恢复

国服仍没有完整样本。TEST-B 已有自然断线到重连失败、标题／载入并回到 GVG 的连续链，也有独立的 `LauncherReady → NoticeReady → ServerEntryReady → CharacterSelection → SceneLoading95 → OpenWorld` 页面链；PIONEER-A 英文双按钮与三角色页只作旧构建语义对照。它们关闭了“同项目是否存在这些页面”的存在性缺口，但没有关闭以下问题：

- Bilibili 登录、扫码、实名和验证码；
- 选服、服务器爆满、排队和维护；
- 更新、资源校验、版本过期；
- 国服角色选择；TEST-B／国服角色创建、删除、多角色默认焦点，以及断线回到哪个页面；
- 重试／重新登录是玩家输入还是客户端自动行为，回到开放世界后原坐标、任务和 Auto 状态是否保留；
- 客户端崩溃和启动器重拉起；
- 多显示器／后台／最小化后的恢复。

首版任何未知连接页面都应归入 `Connection.Unknown` 并停止，不得自动点击“确认”“重试”或“同意”。

## 5. P1：任务导航与委托

需要补齐：

- 点击任务追踪后如何表示“正在寻路”；
- 跨地图、传送、卡普拉和蝴蝶翅膀的优先级；
- 手动移动、进入战斗、队伍召集是否打断寻路；
- NPC 对话、选择题、剧情跳过和交物；
- 委托环数、自动接下一环和最终完成标志；
- 目标不存在、被抢、路径卡住或任务 Bug；
- 60–90 秒无进度看门狗是否足够。

每一环都要以任务进度文本变化作为后置条件，不能只以“页面关了”判断成功。

### 必须分开的状态

### 未知问题

- `Z` 在地图传送、死亡、再战、断线后是否保留状态；
- AutoOn 的稳定视觉标志是什么，动画是否会被遮挡；
- 新增 TEST-B [14 秒卡位候选序列](../../research/evidence/video/auto-blocked-terrain-bv1rg376ue6k/manifest.json)：画面证明“动作／伤害变化但位置无有效进展”，标题称近战自动挂机受地形阻挡；仍未知 AutoOn 标志、选中目标、碰撞原因、自恢复时长和跨职业复现率；
- 无目标时是否移动，多久后算卡住；14 秒短片不能直接成为阈值；
- 锁敌范围、返回原点、抢怪和队伍行为；
- HP／SP 药设置、药品耗尽和低血量停机；
- 背包／负重满后掉落去向；
- 加倍结束是否自动停、降档还是继续；
- 疲劳按击杀还是奖励结算，组队如何计算；
- 自动技能格数量、冷却和战斗中改动限制。

已补直接线索：[快捷用药序列](../../research/evidence/video/twitch-vod-2805739995/manifest.json)显示“HP 低于 70% 时自动使用”勾选态、数量 `36 → 35` 与“背包中没有该道具，无法添加”。这关闭了“是否存在自动用药配置”的存在性问题，但没有键盘输入可视化，不能完全排除一次手动热键；也没有覆盖 `1 → 0`、连续低血量、冷却、自动补槽或死亡前行为。

[高倍三态](../../research/evidence/video/twitch-vod-2804892798/manifest.json)已证明运行倒计时会真实递减；[耗尽页](../../research/evidence/video/twitch-vod-2804807809/manifest.json)证明 `0秒/180分` 是稳定页面状态，同一页中的奖励通知还在九秒内继续变化。仍不能把“耗尽”命名成 `LowTier` 或合并成 `FatigueReached`。

现有 [自动战斗设置帧](../../research/evidence/video/test-closeout-bv1ybny6feze/frames/0107-auto-battle-settings.png)只证明技能列表存在。一则[一手论坛评论](https://forum.gamer.com.tw/C.php?bsn=81475&snA=73)进一步声称 TEST-B 只有六个技能热键、内挂只施放热键上的技能、战斗中不能换格，且猎人辅助施放速度可能明显慢于手动；这些属于单一玩家行为报告，必须逐职业连续复测，不能固化成通用规则。

连续挂机录像还显示技能设置、卡片获得遮罩和挂机收益窗出现时，背景战斗可能继续；因此“打开菜单／弹窗”不能作为已暂停后置条件。停止必须验证目标、伤害、技能和击杀在多帧中真正不再变化。

即使未来获授权，`Z` 是 toggle 也意味着绝不能盲按；必须先识别 Off／On，再发送一次有预算的动作并验证。

## 8. P1：背包、资源与不可逆动作

仍缺少的高风险样本：

- 装备、消耗品、卡片、灵魂残响是否分分页上限；
- 真正满包弹窗与掉落邮件／临时背包；当前只有 `0/300`、`36/300` 正常容量基准；
- 85% 预警阈值能否从 UI 读取；
- 负重与格数的区别；
- 自动整理、分解、出售和扩容确认；
- 公会物资是否会选中已锁定／稀有材料；正常单批已有 `7/8 → 8/8 → 奖励 → 2/4`，第四批另见 `4/8` 发车禁用 → `5/8` 发车可用，但背包扣除、不足操作及点击发车后的终局未知；
- 邮件附件在背包满时的行为。

当前可确认背包容量采用“已用／上限”显示，空包为 `0/300`、正常样本为 `36/300`；玩家报告所称“接近满载”只指卡片／灵魂残响分类且无读数截图，不能升级为通用容量证据。快捷用药页存在启用阈值、槽位、数量变化与配置缺药反馈。它们仍不能回答真正满包、战斗药尽、自动补药或仓库存取。

精炼方面已经能看到[按装备槽列等级与下一步预览](../../research/evidence/video/refine-ui-bv19htn6peo2/frames/0182-refine-slot-level.png)，以及[材料获得途径弹层](../../research/evidence/video/refine-ui-bv19htn6peo2/frames/0212-refine-material-sources.png)。这提高了“只读材料缺口报告”的可行性，但不降低精炼、商店购买和材料跳转的不可逆风险。

没有完整证据时，只读容量并提醒；不自动分解、出售、购买、扩容或提交。

## 10. P2：多人、交易和竞争模式

这些问题主要用于识别并排除，不用于自动化：

- 五人／十人／40 人团队 UI 是否共享锚点；
- 队员离线是否仍占位、有效人数如何显示；
- 匹配取消、角色冲突、队长确认；
- 队内拍卖各阶段和自动出价默认值；
- 摊位税率、价格单位、锁定物品和撤单；
- MVP、PVP、GVG、排行榜的入口和明显场景标志。

一旦场景属于交易／竞争，应路由到 `SafetyStop` 或人工模式。

## 11. 识别开发前的关闭标准

每个场景问题只有同时满足以下条件才标为 `resolved_for_build`：

1. 至少两个独立会话；
2. 环境指纹完整；
3. 正态和相邻混淆态都有样本；
4. 页面动画覆盖至少 3 秒；
5. 标签由两人或一次复核确认；
6. 离线验证集合没有参与模板选择；
7. 在未知帧上不会触发输入意图；
8. 结论只绑定一个明确 build；
9. 下一 build 默认退回 `needs_recheck`。

## 12. 状态维护规则

每个问题采用：

```yaml
id:
status: open | sampling | resolved_for_build | contradicted | removed
region:
channel:
build_id:
evidence_ids: []
resolved_at:
owner:

```

`resolved_for_build` 不等于永久解决。客户端更新、协议变化、UI 布局变化或来源冲突时自动重新打开。
